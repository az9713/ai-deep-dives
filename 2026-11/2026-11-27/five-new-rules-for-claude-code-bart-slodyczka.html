Five new rules for using Claude Code

Claude can write a feature, write the test and report a pass. Slodyczka’s five rules help you decide when that pass is credible and how much authority to give the agent while it works.

Based on the timestamped English transcript and captured frames from Anthropic’s Engineers Stopped Writing Code (Here’s What They Do Instead). Slodyczka distilled the five rules from the Anthropic articles linked below.

  1. Verify the real user flow
  2. Audit your checker
  3. Use the old system as an answer key
  4. Set approval boundaries and a metric
  5. Enforce hard guardrails
  6. Walk through the recipe-search feature
0:59–2:33

1. Verify the real user flow

Give Claude a loop it can run on its own. Make a change, launch the app, perform a real user action, compare the result with the expected behavior, and fix failures. An end-to-end test exercises the feature through the same interface a user would use.

Protect the acceptance check once you’ve reviewed it. Slodyczka suggests a deny rule on the tests folder. Anthropic’s own example is PR review loading its instructions from the base or default branch, so the proposed change cannot rewrite them. For a solo repo, keep the reviewed acceptance test and verification instructions under your control.

2:33–3:56

2. Audit your checker

An evaluation measures behavior against a scoring rule. The grader might be a test script or another model. For model reviewers, require each finding to cite the relevant line, audit a small sample yourself, and see whether another grader or a reworded rubric changes the conclusion. Slodyczka suggests reading five reviews as a starting point. Anthropic also compares model grades with expert labels collected independently.

For a scripted test, deliberately introduce a known bad result in a disposable local change and check that it fails for the expected reason. A search test that still passes when filtering is disabled needs a stronger assertion.

Anthropic’s example of a 34-percentage-point gap compared the same model on the API and on Claude.ai, where the system prompt differed. It illustrates sensitivity to the evaluation setup. Varying the grader is a separate check.

3. Use the old system as an answer key

For a rewrite or refactor, capture representative inputs and expected outputs before changing the code. Run the same inputs through both versions and inspect differences. The old system is an oracle, a reference for the behavior you intend to preserve.

Anthropic’s Rust Messages API passed about 98% of its tests while only about one quarter of compared production inputs initially matched Python. The team found over 100 weakened assertions in the ported tests. To compare both API implementations around a nondeterministic model, Anthropic called the model once and replayed its output to Rust. The input-match chart ends at 99.6%.

Keep the reference data outside the implementation and review any intentional differences. Slodyczka describes an agent proposing to paste old output into the new code to make a check pass. He also recommends recording recurring corrections in CLAUDE.md, with the reason they matter.

4. Set approval boundaries and a metric

Decide what Claude may try in staging on its own and which decisions need you. In the Claude Docs stress-testing loop, Claude could try reversible fixes and rerun the test. Changes to the database schema or document storage required human approval.

Slodyczka suggests putting an “Ask me first” list in CLAUDE.md and picking one clean signal to optimize, such as the number of passing search tests. Keep the minimum conditions the system must always satisfy. The Claude Docs team checked that documents opened quickly and that acknowledged edits survived. A better score is meaningful only while those conditions hold.

8:27–10:29

5. Enforce hard guardrails

Use permission rules for tool access, hooks for actions you need to intercept, and sandboxing to restrict what shell commands can reach. Slodyczka distinguishes Claude’s judgment in auto mode from controls you can enforce outside the model.

The pictured Read(./.env) rule covers Claude’s file tools and some recognizable shell commands. Claude Code’s docs explain that arbitrary subprocesses can open files indirectly. To enforce the boundary across shell commands, use the operating-system sandbox with file restrictions and disallow unsandboxed retries.

10:29–11:57

All five rules in a recipe-search feature

  1. Set access and approvals. Keep .env out of Git and limit Claude’s access. Put database changes, recipe deletion and new dependencies on the approval list.
  2. Record existing behavior. Save the current recipe list so the empty-search case can be compared with a known result.
  3. Write the new acceptance test first. Seed three pasta recipes and at least one unrelated recipe. In the live app, type pasta and assert that exactly the three matching recipes appear. Review the test and protect it before asking Claude to implement search.
  4. Exercise the check. Run /verify. In a disposable change, disable filtering and confirm the test fails. Restore filtering and confirm that it passes. Check the empty search against the saved recipe list.
  5. Record what you learned. If case-insensitive search is required, add that requirement to CLAUDE.md and give it its own acceptance case.

What’s Next

Try a deliberate-failure drill on one of your own solo projects. Plant one plausible regression and ask your existing checks to catch it. If they miss it, a new acceptance check will buy you more confidence than another agent reviewing the same green test run.
