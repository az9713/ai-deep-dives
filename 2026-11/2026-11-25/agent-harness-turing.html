AI agent harnesses

How to tell whether an agent needs a better harness, a better-trained model, or both.

1. Identify what the harness does

An agent harness is the runtime software around a language model. It assembles the input the model sees, executes tool calls, enforces permissions, and tracks work across steps or restarts. Ksenia Se opens with a viewer who saw the same frontier models follow instructions in their native apps and ignore an instructions file in Hermes. Sebastian Raschka’s explanation is that post-training can tune a model to the tools and conventions of a particular harness.

2. Read a leaderboard as a pairing

Li and colleagues evaluated 66 configurations across three benchmarks. On Terminal-Bench 4, the ordering of Claude Opus 5 and GPT-6 Astra reversed when both switched from OpenHands to Pi. The gap moved by about 38.1 points on the benchmark’s 0–100 mean-reward scale. The weights for each model stayed fixed.

Mu, Shen and Shu offer a mechanism. In their formal setting, deployed return = harness ceiling − policy mismatch. The ceiling is the return an optimal policy can achieve through that interface. Mismatch is the loss from the deployed policy’s decisions. On MiniWoB++, reversing the order of observation fields left the optimal decisions unchanged and moved success from 85.0% to 19.2%. Treat changes to tool-result serialization as potential behavior changes.

3. Decide what belongs in software

Se uses the operating-system analogy to explain why the surrounding software stays relevant as models improve. A model can decide when to call a tool. The runtime can execute it, apply access rules, and record the result. The same principle gives deterministic checks their value. In the episode’s surgical-checklist analogy, an explicit check catches an omission even when the operator knows the procedure.

Use the harness to change what the model has to reason about

Alex L. Zhang and coauthors study a Recursive Language Model (RLM) harness. Long input lives in a Python workspace. The model can inspect or slice it with code and make smaller model calls on selected pieces. That structure can make each subproblem resemble the short tasks used during training. The paper reports generalization to tasks 2–64× longer in its length experiments. In a separate long-context suite, its trained RLM-27B improved average scores by 26.9% relative over Qwen3.8-27B in the same harness while using roughly half the inference tokens.

Keep the runtime lean and durable

Philipp Schmid compared four harnesses across roughly 350 tasks. Their scores fell within about six points, and the shell-plus-media setup was substantially cheaper than some designs. Each task was run once. Separately, Pi Durable shows how a small agent loop can sit on durable infrastructure. Cloudflare’s integration persists the transcript and work state in SQLite and wakes the agent to continue after interruption.

4. Adapt frozen weights to a fixed harness

Hugging Face froze Qwen3.8-27B and trained one low-rank adaptation (LoRA) per harness for Pi, Hermes Agent, and OpenCode. LoRA represents a weight change as a product of two small matrices. The team trained those changes with reinforcement learning inside each real agent loop. The video compares the roughly 320 MB half-precision adapter to a device driver. That size describes the add-on weights in the format shown.

For Pi on Terminal-Bench 2.1, Hugging Face’s headline comparison reports 39% → 55% pass@1 and 2.9K → 1.5K average tokens per task. Pass@1 measures the share of tasks solved in one attempt. In the separate matched-task comparison used for the merge evaluation, Pi’s SWE-bench Pro specialist went from 40.0% to 64.0% on tasks graded by every run. Hermes went from 29.4% to 43.1% on its corresponding subset.

Merge specialist adapters and check the trade-off

The adapter updates had layerwise cosine similarities near 0.01–0.02 in the episode’s comparison. Cosine similarity measures directional alignment. Hugging Face concatenated three rank-32 adapters into a rank-96 super-adapter with no additional training steps, and evaluated scaling choices. On the six matched harness–benchmark pairs, its mean pass@1 moved from 39.5% to 49.0% with thinking off and from 55.5% to 63.5% with thinking on.

For Pi’s matched SWE-bench Pro tasks with thinking off, the specialist reached 64.0% and the merged adapter reached 46.0%. Se also points out that Pi compacts context as it fills while Hermes can overflow. Compaction shortens the accumulated history, so verify whether it preserves file paths and error traces that later steps need.

5. Diagnose the first failure before intervening

Yuan Tian and coauthors classify failed trajectories by the first failure signal. A trajectory is the sequence of observations and actions in one run. Start there when an agent produces a weak result after several retries.

6. Carry the reason for each harness change

Harness² holds model weights fixed while an optimizer proposes, probes, and composes harness edits. In one reported WorkBuddy-Bench setup, one refinement step improved GLM-5 by 11.5 points. The framework also learns from past edits to guide later refinement.

Self-Improvement Memory (SIM) gives the harness optimizer a record of the problem, the edit’s rationale, its predicted and observed effects, and the evaluation context. Se shows a workspace example where a harness evolved for Claude Opus 5.5 and copied to Gemini 3.0 Flash took the score from roughly 74 to 68. Continuing optimization with SIM took it to roughly 85. In a separate analysis of ten paired coding continuations, the paper reports a mean gain of 2.36 points over continuing with the harness alone.

Define the expected tool inputs and outputs, permission checks, persisted state, recovery behavior, and audit events before a model swap. Verify those contracts alongside task scores. The episode closes by asking where you want that long-lived infrastructure to live.

What’s Next

Run a 2×2 experiment on one workflow you care about. The following exercise applies the episode’s reasoning to your own agent. For a first run, use 20–30 held-out tasks with independent success checks, such as a fixture test for a small coding change or an exact answer check on a data task.

  1. Run base weights and adapted weights in both your baseline harness and one revised harness. Use one purposeful revision, such as surfacing the complete error trace or changing how observations are presented. Use an adapter trained independently of the held-out tasks.
  2. Run the same tasks in all four cells. Keep the tool permissions, grader, and budget fixed. Log task success, first failure, tokens, attempts, and elapsed time. Count failed and timed-out runs in total spend. Report cost per verified pass when there is at least one pass.
  3. Compare the adapter’s lift in the revised harness with its lift in the baseline harness. Repeat variable runs and inspect a few tasks whose outcomes flipped before drawing a conclusion.
  4. For each edit, record the symptom, why the edit should help, what you expected, what happened, and how to reproduce or undo it. When you swap models, retest tool contracts and replay past failures with that history in hand.

Interaction = (adapted − base) in the revised harness − (adapted − base) in the baseline harness. Use the same success metric in all four cells. A large interaction tells you the benefit of the adapter depends on the runtime it is paired with.
