1. Follow a pull request through the three agents

A pull request (PR) proposes merging changes from one Git branch into another. Christian compares the work after a PR opens to getting a newspaper article published. Someone reviews it, checks run, the author fixes problems, and someone signs off. Faster code generation makes that queue more visible.

2. Run /ship on your own PR

Personal command and team approvals. Christian introduces /ship alongside all three agents. Anthropic documents the personal command as opening or updating a PR, reviewing it, and working on follow-up in your session. You handle the merge under your GitHub rules. The repository’s configured Claude Approvals policy supplies any team approval decision.

  1. Check the tools. For the GitHub exercise, use Claude Code 2.1.331 or later so the watch can push fixes, GitHub CLI 2.63 or later, and Git 2.38 or later for integrating new branch commits. Authenticate gh with gh auth login if needed. Anthropic documents that the watch is unavailable on native Windows. If you use WSL, check the versions and sign-in inside that Linux environment.
  2. Prepare one small change. In a GitHub test repository you control, start from a clean checkout of the default branch. Create a feature branch and edit one README sentence. Review the diff, then commit just that file. A prior commit is especially helpful for a public repository, where /ship leaves uncommitted edits out. Confirm that the final git status --short contains no unrelated changes or untracked files and that the commit includes no secrets.

  1. Start Claude Code in that checkout. At the Claude Code prompt, type the command below. It can commit and push as you after a short cancellation window. There is no confirmation prompt. The work uses your normal Claude Code usage.
/ship
  1. Inspect the GitHub PR. Read Files changed and the review findings. Compare any new fix commit with your original commit, check the CI status, and merge once you’re satisfied and GitHub’s required checks are met.
  2. Keep the watch running if you need follow-up fixes. Keep the session open, the machine awake, and the PR branch checked out. The watch can last up to seven days and can end earlier if the PR closes, the session ends, or other documented stop conditions apply. Use /ship stop to stop it. For your existing PR, /steward starts follow-up without the initial review.

For the first run, turn off auto-merge on that PR if it’s enabled and keep permission prompts on. Use the watch in a repository where you trust the people who can push to your branch or merge to its base. The watch can run programs from the checkout using your credentials.

3. Read the policy before you automate approval

Christian walks through an Anthropic example stored at .claude/approvals.yml. Approvals reads the copy on the default branch. A rule matches changed file paths, defines the default number of human approvals (seats), and can specify an override for a condition such as a passing Claude Code Review.

Change in the exampleDefault decisionIf Claude Code Review passes
Most codeTwo human seats. Claude can comment.One human seat. Claude may approve.
docs/**Two human seats. Claude can comment.Zero human seats. Claude may approve.
services/billing/**Two people who did not author the PR. At least one must be from Payments. Claude can comment.The billing rule retains the human requirements and comment-only permission.

A human seat can be filled by the author unless the rule excludes authors. A one-seat rule can therefore allow a PR to pass with zero independent human reviewers. The billing rule explicitly excludes authors. Claude’s approving review can also satisfy a GitHub approval-count requirement.

Approval and merge are separate events. A zero-seat result allows the approval policy to pass without a human. GitHub still applies its checks and branch rules. With auto-merge or a merge queue, GitHub can merge once the applicable conditions are met.

4. Pilot the repository-wide workflow

The organization rollout uses a connected GitHub repository and a Claude Team or Enterprise organization. An owner sets it up under Organization settings → Claude Ship. The three agents can take part automatically under the settings you choose.

  1. Start with Code Review on one repository. Set its review depth, trigger, and monthly spend limit. Look at which findings turn into real fixes.
  2. Add PR Steward in Manual mode. Start it on selected PRs with @claude steward. Set its own spend limit and inspect the commits it pushes.
  3. Add approval policy in observe mode. Put the proposed policy in .claude/approvals.yml on the default branch with mode: observe. Compare the predicted decision with the team’s actual decisions on docs-only, ordinary code, billing, and mixed-path PRs. Check that rules still request claude/code_review where you expect automatic reviews after the policy file lands.
  4. Enforce the check when ready. Set the policy to enforce and make Claude Approvals a required check for the relevant GitHub branch. Recheck the branch’s review counts, who can satisfy them, and whether auto-merge or a merge queue is enabled.

5. What Christian’s examples show

Who can start a fix changes. An Anthropic product manager acted on a customer’s feedback about confusing Analytics API documentation. Claude Tag opened the PR, Code Review found nothing blocking, a human docs reviewer checked the wording, and Claude Approvals passed. The PR merged that evening. The human sign-off in this case and the zero-seat rule in the video are two different examples.

The reported 40% is a relative decline in the share of merged PRs that were reverted. Anthropic reports that its Claude Code team more than doubled merged PR volume from June to September while the revert share fell by more than 40%. Code Review was one part of the team’s broader process. That internal observation cannot isolate the contribution of Claude Ship or predict another team’s result.

Christian’s four catches. The repository-wide service targets Team and Enterprise GitHub repos, it adds token-based usage charges, PR Steward and Claude Approvals are in public beta, and reviews can miss bugs or vulnerabilities. Code Review is generally available. Observe mode can still incur charges for classifiers and policy-triggered Code Reviews. Personal /ship uses normal Claude Code usage.

Christian closes by predicting changes in engineering roles as approval rules become more permissive. The example establishes how teams can change reviewer requirements. Estimating staffing effects would require evidence on workload, defects, and responsibilities outside PR review.

What’s next

Replay a batch of your own PR types in observe mode. Include a docs-only PR, a code PR, and a docs-plus-billing PR. For each, write down the expected independent reviewers before you see the bot’s verdict. Compare the verdicts with your expectations, then measure time to merge and how many agent-generated fixes a human had to revise. For a solo software factory, this tests whether the workflow removes waiting or moves work into reviewing its fixes.
