Build a 3D world with Astra + Sol

Astra 6.2 directs the build. Sol 6.2 sub-agents make assets in parallel. A reviewer compares their work with visual references. Blender creates the models, and Unreal Engine turns the layout into a world you can walk through.

Based on the English YouTube transcript and six timestamped screenshots. The prompts, files, and acceptance checks are a suggested way to run the workflow yourself. Watch the original video.

Before step 1

Connect Blender and Unreal Engine to Codex using Model Context Protocol (MCP) servers so the agent can work with both. Chase also uses the Higgsfield MCP for Blender work in the cloud, GPU rendering, and sound design. 3:31 · Setup

Pilot build brief

Build one harbor block with a market square, a short bridge, four houses built from one kit, and a distant lighthouse. Test one first-person route from the square, across the bridge, to an overlook. A small scene gives the swarm a complete Blender-to-Unreal handoff to prove before you scale it up.

  • Astra owns the plan and Unreal level. It defines the conventions, queues jobs, accepts reviewed assets, and performs the merge and import.
  • Sol workers own individual asset jobs. Give each worker its own Blender file or working directory so workers can build at the same time without writing over each other.
  • The reviewer owns the verdict. Give it the same reference bundle plus the rendered views and import checks. Require evidence for each verdict.

Paste into Codex · Verify setup

Inspect this workspace and identify the installed Blender and Unreal Engine versions, the active .uproject, and the available Blender and Unreal MCP tools. Create a temporary 1 m test cube in Blender. Use the project’s current import path to bring it into a scratch Unreal level, with a neutral material and simple collision. Verify its dimensions, orientation, origin, and material in Unreal and show one viewport capture. Record the successful export and import settings and the exact tool or step that failed if you find a blocker. List the available model choices and sub-agent controls. Report Higgsfield availability if configured.

Ready to build when the cube imports at the expected size and can be inspected in Unreal. This catches a broken connector, scale mismatch, or import problem while the project is still small.

Step 1

Plan it with reference images

4:42 · Chapter start

Start with a world concept or a visual reference and turn it into a set of images that Codex can build against. Chase used a top-down town plan, a lighthouse reference, and references for different types of houses. The map gives the world its layout. The individual images give the reviewer a target for each asset.

Output · A town plan and asset references that the builders and reviewers share.

Turn references into a brief the workers can use

  1. Create a top-down map with rough dimensions, waterline, elevations, player spawn, route, and landmark anchors. Mark where the bridge meets the street and where the lighthouse should become visible.
  2. Collect a wide mood reference, an eye-level street view, and a front and side view for each hero asset when available. Annotate each with what to match, such as roof silhouette and masonry color, and where workers may vary the design.
  3. Write a small asset list with stable IDs, source references, expected size, and dependencies. Decide which pieces repeat, such as walls and shutters, and which need their own model, such as the lighthouse.

Paste into Codex · Plan the harbor

Act as the lead for a small playable harbor scene. Read the images in references/. Create scene-brief.md, an annotated top-down plan, and an initial asset-jobs.csv. Show the player route from square to bridge to overlook and mark the expected lighthouse sightline. For each major asset, record a reference path, target dimensions or an explicit assumption, the visual traits to match, and which traits may vary. Identify conflicting or missing references and propose the smallest blockout that settles them. Finish with a brief ready for human review.

Ready for the gray box when each major structure has a position and approximate scale, the walk has a start and finish, and each hero asset has a reference a reviewer can use.

Step 2

Test it as a gray box

7:11 · Chapter start

Block out the town in Blender with simple shapes, then import it into Unreal and walk through it. Chase uses boxes for buildings and a pole for the lighthouse. This is the stage to fix the layout and how it feels to move around before investing time in detailed models.

Output · A playable layout with the major structures and routes in place.

Prove scale, circulation, and sightlines

  1. Build only the pieces that control movement or composition first. Use primitive meshes for terrain, decks, stairs or ramps, building volumes, and the lighthouse. Name placeholders by the same IDs you will use for finished assets.
  2. Import into an Unreal blockout level. Set the player start and basic collision on walkable surfaces. Add three saved viewpoints, for example C01_Spawn, C02_Bridge, and C03_Overlook.
  3. Walk the route at player height. Check width and clearance at pinch points, stairs and changes in elevation, and where the player finds the next landmark. Fix the route in the blockout and record any change to the plan.

Paste into Codex · Gray-box and test

Build the agreed layout with primitive Blender geometry and import it into a dedicated Unreal blockout level. Set player start and basic collision along the square-to-overlook route. Save three cameras using the plan’s checkpoints. Export a placement table with asset ID, position, rotation, scale, and units. Capture the three views and list any failed clearance, elevation, or landmark checks. Report what you could verify in the editor and give me the exact route to walk in Play In Editor.

Ready for detailed assets when a person can walk the whole route without getting stuck or falling through geometry, the key sightlines work, and you have saved the approved layout and cameras for later comparison.

Step 3

Build the assets with sub-agents

8:09 · Chapter start

Break the detailed work into modular pieces. Chase had Codex build doors, shutters, walls, and roof components in Blender, then reuse the kit to create 15 house variants. Astra distributed the asset jobs to Sol workers. A reviewer compared the results with the references, sent misses back for revision, and returned accepted work to Astra for sign-off.

Chase used Higgsfield to run Blender in the cloud and render previews from multiple angles when parallel work would have taxed his local machine. 10:20 · Cloud Blender and GPU rendering

Output · Reviewed Blender assets ready to import into Unreal.

Give the swarm bounded jobs

  1. Agree on scale, origin, module sizes, material names, and the export path using the tested cube. For wall segments, choose a consistent snap point. For a rotating object such as a door, choose its hinge as the pivot and verify it after import.
  2. Start with a vertical slice of the kit, for example one wall, one shutter, and one roof piece that fit together. Approve that slice before fanning out. Divide the rest by asset family and give each Sol worker an isolated output path.
  3. Require comparable review views. Start with front, side, and three-quarter renders under consistent lighting. Include one close-up when a detail drives the decision. Ask the reviewer to identify a visible mismatch, the view where it appears, and the smallest change that would fix it.
  4. Send accepted assets through an Unreal test import. Check dimensions, pivot, material assignments, and collision where the player touches them. Keep the editable Blender source, the export, and the review decision together. Epic’s FBX static-mesh pipeline

Paste into Astra · Dispatch jobs and review evidence

Read scene-brief.md, the approved blockout, and asset-jobs.csv. First build and import one modular kit slice to verify the shared scale, pivots, snap points, and materials. Then dispatch independent asset jobs to Sol 6.2 workers. Assign each worker its own folder and supply its reference views, dimensions, hard requirements, and the expected Blender source, export, and review renders.

For every result, ask a separate reviewer to compare matching views and report pass, revise, or escalate with concrete evidence. Route revisions back to the same worker. Use two revision rounds as an initial pilot limit, then escalate persistent misses with options. Sign off on passing assets and record their export paths and review evidence for Unreal import. If exact model assignment is unavailable, report the actual worker configuration used.

Cloud rendering decision. Time one local multi-view render and one cloud job, including upload, queue, render, and download. Compare elapsed time and credits before sending a whole batch. Keep the same review views in either case.

Ready to assemble when every asset needed for the route has passed review, the modular parts fit together, and at least one asset from each family imports with the expected scale, pivot, and materials.

Step 4

Assemble the world in Unreal

11:44 · Chapter start

Import the reviewed assets and use the approved gray box as the placement plan. Chase recommends a second review loop for the assembled Unreal scene. At this stage, the reviewer compares the scene as a whole with the intended world. The video shows a review sheet that holds the camera positions fixed to make changes easier to see.

Output · An assembled scene that has been reviewed against the plan.

Replace placeholders in controlled batches

  1. Duplicate the approved blockout level for assembly. Map each placeholder ID to an approved asset and preserve the original placement and camera transforms as baselines.
  2. Import and place the walkable structures first, then buildings and landmark assets, then lighting and set dressing. After each batch, check the spawn, the bridge joints, the stairs, and the overlook again.
  3. Re-render the saved views with the same camera and resolution. Compare like-for-like lighting when judging geometry. Ask the scene reviewer to check composition, seams, repeated patterns, missing materials, floating objects, and changes that obscure route landmarks.

Paste into Codex · Assemble and compare

Duplicate the approved Unreal blockout into an assembly level. Import accepted assets and replace placeholders using asset IDs and the placement table. Keep the saved cameras. Install route-critical geometry first, confirm collision at the bridge and overlook, and then add buildings, landmarks, and set dressing. For each saved camera, generate a same-camera before/after pair. Ask a reviewer to record each issue with a camera ID or world location, the affected asset, and a suggested fix. Return the assembly level path, import notes, comparison sheet, and any remaining blockers.

Ready to playtest when the build matches the agreed route and composition, required assets load with their materials, and the scene review leaves no blocked segment.

Step 5

Playtest it on foot

12:18 · Playtest discussion

Launch the Unreal world and walk through it in first person. Give Codex specific feedback on what looks or feels wrong from the ground, then iterate. The market walkthrough shows one handoff where the slowest frame fell from 228.57 ms to 17.93 ms after a fix.

Output · A playable world refined with feedback from an actual walkthrough.

Make every issue reproducible

  1. In Unreal’s Play In Editor mode, follow the same route from the same spawn. At each checkpoint, inspect movement, collision, sightlines, lighting, and any visible or audible transition. Test the route in reverse when entry angles differ.
  2. For a hitch, use stat unit to see frame, game-thread, rendering-thread, and GPU times. Capture a trace with Timing Insights when you need per-frame detail around the problem. Keep machine, resolution, quality settings, and route comparable across runs. Epic’s stat commands · Timing Insights
  3. Log the issue with the checkpoint, steps to reproduce, observed result, expected result, and evidence. Fix one likely cause at a time, repeat the route, and update the issue with the before/after result.

Paste into Codex · Reproduce and fix a playtest issue

Use the saved square-to-overlook path. At checkpoint C02_Bridge, start from the market spawn, cross the bridge at normal walking speed, and turn toward the lighthouse. Record whether the hitch or traversal issue reproduces. Save the world location and steps. For a performance issue, capture frame-time evidence and note the machine, render settings, and whether the run was cold or warmed up. Identify one likely cause, make one scoped fix, and replay the same route and settings. Return the before/after evidence and list any new defects or remaining uncertainty.

Pilot complete when the full route is repeatable, traversal blockers are closed, and you have a saved Unreal level, a short walkthrough, and evidence for the fixes you made.

When to scale the swarm

Run the same small kit once with a single agent and once with Astra, Sol workers, and a reviewer. Hold the references and acceptance checks fixed. Record elapsed time to the last accepted asset, first-pass acceptance, revision count, and cloud credits. Include import and review time. Those results tell you whether adding workers is speeding up production or moving the queue to review and Unreal integration.
