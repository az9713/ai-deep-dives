Beyond Software Factories

Ray Amjad’s case for giving a persistent engineering lead the whole queue, then letting its workers adapt how they build, review, and verify each change.

Three ways to organize the work

Amjad compares agent teams you manage through conversation with software factories you define and measure in code. His hybrid combines a lead’s view of all active work with a written procedure that workers can adapt to each task.

Transcript · 0:00–0:30 and 9:20–10:32

1. Agent teams give you a role to talk to

Transcript · 1:03–3:23

Amjad creates a Devin Technical Writer bot and asks it to keep documentation current. He shows Slack as another entry point into the same session and mentions iMessage as an option. The bot has its own identity, permissions, memory, usage limits, and connections. In the demo, the lead delegates execution to a worker thread in a larger, separate sandbox. A sandbox is an isolated environment where an agent can run tools and work on files.

Leads steer work and workers execute it

Transcript · 3:23–5:12

A person can speak directly to a domain lead or go through a chief of staff that coordinates several leads. The lead can message and steer its workers. A worker can create a temporary subagent for a focused review or research pass. Amjad points to Brian Armstrong’s chief-of-staff diagram and Grok Bot’s delegation to separate Cursor Cloud Agents as related examples. His judgment of the Grok models comes from a short personal trial.

Hierarchy creates two kinds of coordination cost

Transcript · 5:13–6:37

  1. Too many layers. One chief of staff per project can lead to another above them, and personal chiefs of staff may then give overlapping direction to the same leads.
  2. Too many permanent roles. Promoting builder, reviewer, and verifier into separate leads creates handoffs for every feature. The worker can use those same roles temporarily while retaining the task context.

2. Factory as code makes the workflow measurable

Transcript · 6:37–9:18

In Amjad’s account of Zach Lloyd’s argument, a factory can define its stages, information flow, and gates in a versioned file such as factory.yaml. A gate is a condition that controls whether the workflow advances, retries, or routes work elsewhere. With comparable runs, you can change one part of the workflow and measure the effect on quality, throughput, and cost.

The replay that removed a planning layer

Amjad reports replaying past pull requests with and without a planner–subplanner hierarchy. His scoring found no measurable quality change. The captions give mean cost per pull request as $940 before and about $630 after, roughly a one-third reduction. The segment gives no sample size or uncertainty estimate, so the result describes his tested setup. 7:21–7:58

Give each task its own harness and compute

A harness is the machinery that organizes model calls, tools, and checks. Amjad’s example starts with a specification, an implementation agent, and a sized sandbox. It forks copies of that environment for code review and user-flow discovery in parallel. A structured review result can send work back to the original sandbox for fixes. Separate copies can verify each discovered flow and collect evidence before a final approval step. 7:58–9:18

3. The hybrid keeps a shared procedure and lets workers adapt

Transcript · 9:20–11:34

Amjad prefers writing the task lifecycle in a skill, a file that gives an agent a reusable procedure. The engineering lead hands the procedure to each worker. Inside the worker’s task, the builder implements the feature, a reviewer returns findings, and a verifier sends back flows that fail. The task can repeat whichever step the evidence requires.

The lead sees the work across sandboxes. If a new task is about 90% covered by work in progress, the lead can pass the remaining requirement to the existing worker. Amjad also proposes a weekly routine that varies the procedure and replays old pull requests, tracking quality alongside time, compute, and tokens. He flags overfitting as a risk when repeatedly tuning against the same examples. 10:07–11:30

4. Give implementation one owner and split leads by domain

Transcript · 11:34–14:55

Amjad uses a QA bot that discovers a bug to illustrate the ownership problem. QA might fix it faster, while the factory lead may have accumulated more relevant engineering context. His design gives one factory lead ownership of the implementation queue. QA, growth, customer support, and social monitoring can submit work directly or through a queue such as GitHub Issues. The lead still runs several worker sandboxes in parallel. He keeps a human role in deciding which new features to build because he finds the agents more dependable at maintenance and improvements. 11:58–13:39

Use handoff frequency to test a proposed boundary

Amjad’s heuristic is to ask how often two leads would have to exchange context. Company accounts and value-added tax (VAT) would need to talk for nearly every transaction in his example, so he keeps them in one bot. Apply the same test to a planner, implementer, reviewer, and verifier that would hand off every feature. One lead can own the domain and use those roles inside the task. 13:42–14:47

5. Personal agents can compete for a team’s budget

Transcript · 14:55–16:29

Amjad illustrates Anthropic’s Worse Together study with six jobs, three high-value and three low-value, and a token budget that cannot cover them all. A shared coordinator completes the three high-value jobs. In the peer-to-peer example, individual agents spend some budget on lower-value work, and one high-value job is left unfinished. The team objective depends on how the shared budget is allocated.

What the study adds. The six jobs are the video’s illustration. In the paper’s simulated API-budget environment, the researchers found that a designated team lead with explicit priorities could close the gap for the tested Claude models. That mitigation was specific to the budget environment. Read the study.

Amjad’s expectation for 2027

He expects a recurring cycle. New models enable products and use cases. Builders turn those uses into evaluations and add harness logic to improve performance. Later models trained on those evaluations may absorb some of the behavior the harness supplied. This is his forecast about where special-purpose scaffolding may lose value. 16:29–16:51

What’s next

Application inspired by the video’s replay test and hybrid design · 7:17 and 9:51

Replay the same work through a fixed workflow and an adaptive worker

  1. Choose past pull requests with known acceptance checks. Start each replay from the same repository state and give both variants the same specification, model, and budget.
  2. Compare a fixed build–review–verify pipeline with a worker that can choose when to loop through the same roles. Keep acceptance checks the same in both variants.
  3. Record acceptance-pass rate, cost per accepted change, elapsed time, reviewer rework, and duplicate tasks merged by the lead. Hold back some tasks to check whether any measured improvement generalizes.
  4. Give both variants an intentionally overloaded queue. Check which high-priority tasks finish before the budget runs out. This tests coordination separately from coding ability.
